keelson · rib adme · design mockup

Access is the daily work on an ADME instance, so the rib opens on an access desk and every change is a previewed plan

The design is 3 tabs for 36 identities (32 people and 4 applications) and 13 seismic subprojects. A fresh first paint costs about 12 API calls; a repeat visit paints from the disk cache with none.

Today. An ADME instance is typically run with ad hoc scripts, az and Graph calls, and a tracker kept by hand. An invitation to a new address can resolve to an existing guest and return that guest's object id; acting on that mistaken identity can strip access from the wrong person. Seismic access sits in groups named by UUID (data.sdms.opendes.alpha.3f9a…e1.admin), acceptance state lives only in Graph, and no batch change has a dry run.

The rib. The ADME Access tab lists who needs attention and why, shows every person against roles and seismic grants by name, and routes every write through one plan: a form produces a dry run, the plan sheet classifies each identity before any invitation, Apply re-checks, writes serially, verifies the effective group count and appends to the tracker. It works from the operator's Azure CLI sign-in, so the rib holds no secret.

Limits. Every name and count on this page is sample data. Nothing is built, and nothing was called live. Shelling az through ctx.getExec() is unverified and the whole design rests on it. The collision can be detected and halted, not prevented, once an invitation email is sent. ADME Data is read-only in the first take: it creates, extends and deletes nothing.

  • Rib · composes boards, holds plans, makes every call
  • Azure CLI sign-in · the rib calls ADME and Graph as the operator
  • ADME services · entitlements, legal, storage, search, seismic
  • Entra Graph · users, invitations, roster group

The prototype below is the Keelson window with the three ADME tabs, drawn with the board renderer's own DOM and the rules from app.css. How it is organised

Each tab covers one part of the instance. The tab labels carry the rib name because the top bar has no overflow rule and other ribs sit beside them. The Connection region is the footer of all three tabs under one snapshot key.

Because an inspector replaces whatever the drawer showed, a running plan stays visible in the Operation region on the ADME Access tab, and Recent changes lists every plan that is staged, paused or applied.

One way to change anything

Every form submits Preview plan and never mutates. A plan is rib-held state with an id and a hash, and it expires after 30 minutes. The plan sheet classifies each address (existing guest, restorable from deleted items, will invite, ambiguous) before any invitation is sent. The worked example adds 2 people to Pilot: 4 calls will change something, and 1 address is blocked because it resolves to Rachel Kim's existing account.

During Apply each call carries the correlation id keelson-adme-<planId>-<n>, which joins to OEPAuditLogs. A 409 counts as already true. Adds get a simple confirm ("Apply 4 changes?"); removals need a typed subject, for example typing Rachel Kim to remove her (2 membership deletes, Entra guest kept). Removing a whole cohort and the adme_plan_* agent tools come later.

Figure 2 follows a plan from the form to the tracker, with the three ways Apply stops.

Limit

The collision is detected after the invitation email has gone out. Classifying by mail and otherMails first catches the cases Graph can see; a new address on the same home identity is visible only when the object id comes back.

How it reaches the instance

The rib runs in-process in the Keelson server: no workflow, no cadence, no stored credential. The connection profile is six non-secret values (host, partition, entitlements domain, tenant id, ADME app id, roster group id).

Figure 3 shows the four actors and the path of every call.

Sign-in

The rib uses the operator's Azure CLI sign-in. Before each batch of calls it asks az for a token again with the two commands below, so token lifetime never appears in the UI. Every ADME request sends Authorization: Bearer and data-partition-id: opendes.

The only state the operator sees is "sign-in needed": a card with az login --tenant 1f2e…9a00 to copy, cached data under a "cached from 13:02Z" chip, and changes paused, with every button that would change something disabled for that reason. A running plan pauses at its step and resumes after sign-in.

# Token for ADME: the resource is the ADME app id, not the instance URL
$ az account get-access-token --resource 4c7d…2b18
# Token for Graph
$ az account get-access-token --resource https://graph.microsoft.com

What Keelson cannot do yet

A rib publishes board snapshots; it does not author UI. These limits, verified against keelson main e7f7314b, shaped the layout.

An unmeasured value is drawn as "?" or a hatched bar and worded "not measured": dataset counts, schemas, and records affected by an invalid legal tag all appear that way.

Open questions

  • Shelling az through ctx.getExec() is unverified. Resolve with a spike before any board work: one composer that signs in through az for both resources and makes one read against ADME and one against Graph.
  • Seismic reads may not behave as assumed. The subproject list returning ACL group names, reading other subprojects' members as tenant admin, and GET /groups/all are untested. Test connection probes each one and writes the capability matrix; the fallback parses data.sdms.* from the operator's own groups and may be incomplete.
  • Aggregate by kind, the schema service and the partition API. Not exercised. The partition API returns 403 to a user sign-in. The capability matrix records each result; until then the tiles read "?".
  • One Connection key on three surfaces. No uniqueness check was found in the host's rib registration. If it fails in practice, three keys share one composer.
  • Confirm on Apply. A confirm fires only on an action marked destructive, so the mockup's brand-toned "Apply 4 changes" with a confirm needs the host change in appendix C. Decide once: wait for it, or treat the plan sheet as the review and let adds apply without a dialog.
  • Expected group counts drift. 33, 39, 46 and 49 change with platform releases. Derive the count from a peer with the same grants, and add a per-person baseline so a known one-off stops counting as an access gap.
  • The tracker is a second source of truth. Cohort, pass end date and history live only in the rib's data dir. Ship import with export in the first take.
  • Strict schemas, unproven primitives. Tabbed actions, table badges, grid and head menu actions have little precedent in existing ribs, and one unknown key blanks a panel. Give every composer a schema test.
  • Action timeout is unknown. Identity resolution for a cohort can take tens of seconds. "Preview plan" should return at once and recompose; Apply runs as a registered op.
  • Nothing was observed running. Three tab labels beside other ribs, an 11-column matrix and narrow viewports were read from CSS only. Check them in the app once the first composer exists.
  • Selection is rib-held and global. Two browser windows share one drawer target and one lens. Accept it for a single operator and say so in the rib's docs.
  • Names, emails and object ids are plain text in snapshot frames and the data dir. Acceptable on a local workbench; state it in the rib's docs.
